Hashing de contraseñas con bcrypt

Las contraseñas nunca se guardan en claro ni con MD5/SHA sin coste. bcrypt genera un hash con salt integrado y un factor de coste ajustable, lo que lo resistente a ataques de diccionario y a hardware GPU/ASIC.

utils/password.js 
import bcrypt from 'bcryptjs';

const RONDAS = 12; // Coste: 2^12. Aumentar con el tiempo.

export async function hashear(plain) {
  return bcrypt.hash(plain, RONDAS);
}

export async function verificar(plain, hash) {
  return bcrypt.compare(plain, hash);
}

// Uso:
// const hash = await hashear('password123');
// const ok   = await verificar('password123', hash);
🚫 Nunca uses SHA-256 puro

Funciones como SHA-256 son demasiado rápidas; un atacante con una GPU puede probar miles de millones de combinaciones por segundo. Usa funciones lentas y con salt: bcrypt, argon2 o scrypt.

Anatomía de un JSON Web Token (JWT)

Un JWT es una cadena compacta firmada que viaja en la cabecera Authorization: Bearer . Se compone de tres partes separadas por punto: header.payload.signature.

Estructura de un JWT 
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9   ← Header (alg, typ)
.eyJzdWIiOiIxIiwiZW1haWwiOiJhbkB4LmNvbSIsInJvbGUiOiJ1c2VyIiwiaWF0IjoxNzAwMDAwMDAwLCJleHAiOjE3MDAwMDcyMDB9   ← Payload (claims)
.s8f3Kd2Lp9QwVn2Xb8Hj3kL9pQz1RwYn4Xm7Vc2A0I   ← Signature (HMAC-SHA256)

// Header
{ "alg": "HS256", "typ": "JWT" }

// Payload
{
  "sub":   "1",                          // ID del usuario
  "email": "an@x.com",
  "rol":   "user",
  "iat":   1700000000,                   // issued at
  "exp":   1700007200                    // expira a las 2h
}
📌 JWT no es encriptación

El payload va codificado en Base64Url, no cifrado: cualquiera con el token puede leerlo. La firma garantiza integridad (no ha sido modificado) y autenticidad (proveído por nosotros). No pongas datos sensibles en el payload.

Flujo completo: Registro y Login

controllers/auth.controller.js 
import jwt from 'jsonwebtoken';
import bcrypt from 'bcryptjs';
import { buscarPorEmail, crearUsuario } from '../services/usuarios.service.js';

const SECRETO   = process.env.JWT_SECRET;
const EXPIRACION = process.env.JWT_EXPIRES_IN ?? '2h';

export async function registro(req, res, next) {
  try {
    const { email, password, nombre } = req.body;
    const existe = await buscarPorEmail(email);
    if (existe) return res.status(409).json({ error: 'Email ya registrado' });

    const passwordHash = await bcrypt.hash(password, 12);
    const user = await crearUsuario({ email, passwordHash, nombre });

    res.status(201).json({ id: user.id, email: user.email, nombre: user.nombre });
  } catch (err) { next(err); }
}

export async function login(req, res, next) {
  try {
    const { email, password } = req.body;
    const user = await buscarPorEmail(email);
    if (!user) return res.status(401).json({ error: 'Credenciales inválidas' });

    const ok = await bcrypt.compare(password, user.password);
    if (!ok) return res.status(401).json({ error: 'Credenciales inválidas' });

    const token = jwt.sign(
      { sub: user.id, email: user.email, rol: user.rol },
      SECRETO,
      { expiresIn: EXPIRACION }
    );
    res.json({ token, usuario: { id: user.id, email: user.email, rol: user.rol } });
  } catch (err) { next(err); }
}
POST /api/v1/auth/login

Body: { "email": "...", "password": "..." }. Respuesta: { "token": "eyJhbGci...", "usuario": {...} }.

💡 Devuelve el mismo error para "email no existe" y "password incorrecta"

Si distingues los mensajes, un atacante puede enumerate qué emails están registrados. Devuelve un genérico "Credenciales inválidas" en ambos casos.

Refresh Tokens

Un access token de corta duración (15 min–2 h) minimiza el impacto si se filtra. Un refresh token de larga duración (días/semanas) se usa para obtener nuevos access tokens sin pedir login de nuevo.

CaracterísticaAccess TokenRefresh Token
DuraciónCorta (min–horas)Larga (días)
UsoEn cada petición autenticadaSolo en /auth/refresh
AlmacenamientoMemoria JS / sessionStorageCookie httpOnly + secure + SameSite
RevocableNo (stateless)Sí (almacenado en BD/blacklist)
Nuevo access token a partir de un refresh válido 
export async function renovar(req, res) {
  const refreshToken = req.cookies?.refresh_token;
  if (!refreshToken) return res.status(401).json({ error: 'Falta refresh token' });

  try {
    const payload = jwt.verify(refreshToken, process.env.REFRESH_SECRET);
    const access = jwt.sign(
      { sub: payload.sub, rol: payload.rol },
      process.env.JWT_SECRET,
      { expiresIn: '15m' }
    );
    res.json({ token: access });
  } catch {
    res.status(401).json({ error: 'Refresh token inválido, vuelve a iniciar sesión' });
  }
}

RBAC: control de acceso por roles

El middleware requerirRol valida que el usuario autenticado tenga uno de los roles permitidos para esa ruta.

middlewares/rbac.js 
export function requerirRol(...rolesPermitidos) {
  return (req, res, next) => {
    if (!req.user) return res.status(401).json({ error: 'No autenticado' });
    if (!rolesPermitidos.includes(req.user.rol)) {
      return res.status(403).json({ error: 'Permisos insuficientes' });
    }
    next();
  };
}

// Rutas
router.delete('/usuarios/:id',
  verificarToken,
  requerirRol('admin'),
  borrarUsuario
);

Checklist de seguridad para producción

  • ✅ Genera JWT_SECRET con al menos 32 bytes aleatorios (crypto.randomBytes(32).toString('hex')).
  • ✅ Ajusta una expiración razonable (2h access tokens, 7d refresh).
  • ✅ Cookies con flags httpOnly, secure y SameSite=Strict/Lax.
  • ✅ Configura CORS estricto (solo orígenes permitidos, no *).
  • ✅ Rate limiting en /auth/login y /auth/register para frenar brute force.
  • ✅ Usa helmet() para cabeceras de seguridad por defecto.
  • ✅ Valida el esquema de entrada con Zod, Joi o express-validator.
  • ✅ Permite invalidar sesiones revocando el refresh token en BD.
  • ✅ Logout en el cliente delete el token y, en backend, black-listea el refresh.
  • ✅ Registra los intentos de login fallidos y dispara alertas tras N fallos.
⚠️ OAuth/OIDC para producción seria

Para apps con muchos usuarios o requerimientos de SSO, considera delegar la autenticación a un proveedor OAuth/OIDC (Auth0, Clerk, Firebase Auth, Keycloak) en lugar de gestionar JWT tú mismo. Eso centraliza seguridad, MFA y gestión de sesiones.
